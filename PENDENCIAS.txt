## ⚠ SEGURANÇA — POST /feedback/{videoId} e provavelmente GET /getFeedbacks
## vazam o hash de senha (bcrypt) e a entidade User completa

CONFIRMADO AO VIVO (não é teórico): chamei POST /feedback/1 com um usuário
autenticado normal e a resposta (113KB!) inclui, entre outras coisas:
  "password":"$2a$10$pgTmJZOvQuRItQLZ2Mbpo.T9pQeoiJ3n7xQifkB8XpG99ho6k76/O"
E o objeto completo da entidade JPA `User` (LastActivity, authorities,
accountNonExpired, hibernateLazyInitializer, etc.) dentro de "video.creator"
E TAMBÉM um "video.creator.videos[].creator..." que se repete recursivamente
(vídeo -> criador -> lista de vídeos do criador -> criador de cada um deles
-> ...), inflando a resposta a mais de 100KB para um único feedback.

Isso é uma FALHA DE SEGURANÇA real (exposição de hash de senha, mesmo que
com custo alto pra quebrar, não deveria nunca estar em uma resposta HTTP) e
também um problema de performance/DoS potencial (payload recursivo enorme
para uma ação simples de curtir).

Causa (lida no código antes desta sessão): FeedbackResponse.video e
FeedbackResponse.user retornam as entidades JPA Video/User diretamente, em
vez de DTOs próprios, então o Jackson serializa tudo que está acessível via
getters, incluindo password e relações @ManyToOne/@OneToMany que criam o
loop.

MITIGAÇÃO NO FRONT: o frontend NUNCA lê nem renderiza feedback.video ou
feedback.user em nenhuma tela hoje (só dispara a ação de like/dislike e
ignora o corpo detalhado da resposta) — não há vazamento pelo lado do
cliente, mas o dado sensível já saiu do backend pela rede assim que a
chamada é feita, então isso precisa ser corrigido no backend
independentemente do que o front faz com a resposta.

SUGESTÃO DE CORREÇÃO (prioridade alta, é uma questão de segurança):
FeedbackResponse.video deveria ser um VideoResponse (DTO), não a entidade
Video; FeedbackResponse.user deveria ser um UserResponse (DTO) ou nem
existir na resposta. Nunca serializar entidades JPA diretamente em
respostas HTTP.

## BLOQUEIO CRÍTICO — GET /video (e provavelmente GET /video/{id}) exige
## autenticação na prática, mesmo sendo documentado/configurado como público

Confirmado ao vivo:
- `curl http://localhost:8080/video` (sem header Authorization) => 500 Internal
  Server Error, corpo genérico sem stacktrace.
- `curl http://localhost:8080/video -H "Authorization: Bearer <token válido>"`
  => 200 OK, `[]` (lista vazia, sem erro).
- `curl http://localhost:8080/video/1` (sem token) => 500 também.

Causa raiz (lida no código-fonte, VideoService.java):
`findAllVideos()` chama `authVerifyService.getAuthenticate()` (linha ~75-77),
que faz `Objects.requireNonNull(SecurityContextHolder...getAuthentication())`
e depois um cast para `(User)`. Como a rota é `permitAll()` no
SecurityConfig, requisições sem token chegam ao controller com
Authentication nulo ou anônimo — o requireNonNull ou o cast falham, gerando
NullPointerException/ClassCastException não tratada. GlobalExceptionHandler
não tem handler genérico para Exception/RuntimeException, então cai no 500
padrão do Spring sem detalhe.

O mesmo padrão existe em `findVideoById()` (linha ~109-115) — mesmo problema
esperado em GET /video/{id} sem token (confirmado acima).

IMPACTO NO FRONT: a Home (feed de vídeos) e a página de vídeo individual só
funcionam hoje para usuários COM SESSÃO ATIVA. Um visitante anônimo (que é
exatamente o caso de uso descrito como "rota pública" no prompt original)
recebe 500 e vê a home vazia/com erro. O frontend já trata isso como
`isError` e mostra um EmptyState amigável, mas o comportamento correto
(navegação anônima ver vídeos publicados) SÓ vai funcionar quando o backend
for corrigido.

SUGESTÃO DE CORREÇÃO (não fiz — é código de produção do backend, fora do
escopo que o dono do projeto autorizou eu tocar):
Remover a dependência de usuário autenticado dentro de
findAllVideos()/findVideoById() (ela não é usada para nada essencial na
resposta, é só efeito colateral de um getAuthenticate() desnecessário para
uma listagem pública), OU trocar getAuthenticate() por uma versão que
retorna null/Optional quando anônimo, tratando esse caso explicitamente.

## POST /auth/register — 500 se bio/profilePhoto/state/country vierem nulos

Confirmado ao vivo:
- Payload sem bio/profilePhoto/state/country => 500 Internal Server Error.
- Mesmo payload incluindo esses 4 campos com string não-vazia => 201, sucesso.

Causa: colunas `nullable = false` em User entity (bio, profilePhoto, state,
country) sem validação (@NotBlank/@Valid) no UserRegisterRequest/Controller.
Cliente que omite qualquer um desses campos causa
DataIntegrityViolationException não tratada pelo GlobalExceptionHandler =>
500 genérico.

MITIGAÇÃO JÁ APLICADA NO FRONT: RegisterPage.tsx agora sempre envia string
vazia ('') para bio/profilePhoto/state/country/linkInstagram/linkYoutube/
linkWebsite quando o usuário não preenche esses campos no formulário (eles
não são exigidos visualmente, mas o payload nunca manda undefined/null).
Isso faz o registro funcionar contra o backend atual.

SUGESTÃO DE CORREÇÃO NO BACKEND: adicionar @Valid no controller e
@NotBlank/@NotNull no DTO para os campos que mapeiam para colunas NOT NULL,
retornando 400 com mensagem clara em vez de 500; ou tornar essas colunas
nullable no schema, já que bio/profilePhoto/redes sociais são
legitimamente opcionais no perfil de um usuário.

## PUT /auth/users/{email} (editar perfil) — mesmo risco do register

Como não existe endpoint "/me" para pré-carregar os dados atuais do
usuário (bio, state, country, links), o formulário de edição de perfil no
front não sabe o que o usuário já tinha cadastrado nesses campos. Um PUT
"parcial" (só alterando nome, por ex.) vai sobrescrever bio/state/country/
links com string vazia, porque o UserUpdateRequest não faz merge parcial
no backend — é um PUT completo.

MITIGAÇÃO APLICADA: ProfilePage.tsx envia string vazia nesses campos (nunca
undefined) para não quebrar com 500, mas isso tem o efeito colateral de
ZERAR esses campos no primeiro "Salvar alterações" que o usuário fizer,
mesmo que ele tivesse preenchido bio/redes sociais no registro.

SUGESTÃO DE CORREÇÃO: adicionar um endpoint GET /auth/me (ou /users/me)
retornando o UserResponse completo com todos os campos do perfil, para o
front pré-popular o formulário antes de qualquer PUT. Sem isso, edição de
perfil vai sempre truncar dados a menos que o usuário retype tudo de novo
a cada vez.

## Follow/unfollow/contador de seguidores inconsistente (testado ao vivo)

Sequência testada com dois usuários reais:
  POST /auth/users/4/follow    => 409 Conflict "já segue"
  POST /auth/users/4/unfollow  => 400 Bad Request "User not already follows"
  GET  /auth/users/4/followers => {"followers":0}  (sempre, antes e depois)

Ou seja: o backend acredita que o usuário JÁ segue (409 ao tentar seguir de
novo), mas ao mesmo tempo acredita que ele NÃO segue (400 ao tentar
deixar de seguir), e o contador de seguidores nunca sai de 0 mesmo com a
relação de follow supostamente ativa.

Causa raiz (código-fonte): a entidade Follow tem um campo booleano chamado
`isActive` (em vez de `active`). Como o Lombok gera o getter `isActive()`
para um campo booleano chamado `isActive`, o Spring Data JPA interpreta o
nome da propriedade de forma ambígua ao derivar as queries
`findFollowByFollowerIdAndFollowedIdAndIsActiveTrue` (usada no unfollow) e
`countByFollowedIdAndIsActiveTrue` (usada no contador de seguidores) —
essas duas queries derivadas não concordam entre si nem com o estado real
persistido, o que explica os resultados contraditórios acima.

IMPACTO NO FRONT: o botão "Seguir" na página de vídeo e o contador de
seguidores no perfil NUNCA vão refletir a realidade — o contador fica
sempre em 0 e tentar seguir/deixar de seguir alterna entre erros
confusos para o usuário.

SUGESTÃO DE CORREÇÃO: renomear o campo da entidade Follow de `isActive`
para `active` (mantendo/ajustando @Column(name="is_active") se necessário
para não quebrar a coluna já existente no banco), e atualizar as queries
derivadas no FollowRepository e as chamadas em FollowService para usar
`Active` em vez de `IsActive` nos nomes dos métodos.
